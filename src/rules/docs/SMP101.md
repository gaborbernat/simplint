## What it does

Checks for module-level variables that are assigned once and not annotated `Final`. A name counts as reassigned when the
module binds it more than once, including augmented assignment and assignment through `global` in a function. Dunder
names, class-like names such as `Alias`, tuple unpacking, names already annotated `Final`, `ClassVar` or `TypeAlias`,
and values built by `TypeVar`, `ParamSpec`, `TypeVarTuple`, `NewType`, `TypeAliasType`, `NamedTuple` or `TypedDict` are
skipped.

## Why is this bad?

Without `Final`, a reader has to search the codebase to learn that a module variable never changes. With it, the type
checker rejects any reassignment, here or in another module.

## Example

```python
TIMEOUT = 30
LIMIT: int = 10
```

Use instead:

```python
from typing import Final

TIMEOUT: Final[int] = 30
LIMIT: Final[int] = 10
```

## Fix safety

The fix is safe. It wraps an existing annotation in `Final[...]`. Without an annotation, it adds `Final[int]`,
`Final[float]`, `Final[str]`, `Final[bytes]` or `Final[bool]` when the value is a literal of that type (f-strings count
as `str`); any other value, such as a call, a negative number or a container, gets no fix because its type cannot be
read from the text. The fix writes `Final` when the name is already bound and `typing.Final` after `import typing`;
otherwise it adds `Final` to the first `from typing import`, or inserts `from typing import Final` after the module
docstring and `__future__` imports. A `Final` imported only under `if TYPE_CHECKING:` does not count as bound when
annotations are evaluated eagerly (before Python 3.14 without `from __future__ import annotations`), so the fix adds a
runtime import.
